Solution: Who Killed Checkout?

KillerDeploy Dave — payment-service v2.3.1 (08:58) reduced maximumPoolSize from 50 to 5 (FINOPS-482). No load test and 100% rollout.
WeaponDB connection pool exhaustion. With 3× traffic, only 5 connections exist. Each payment holds a connection for ~220 ms (including the PayFast call, see Exhibit F), so requests queue. After 30 s, Connection is not available, request timed out after 30000ms → checkout 504.
AccompliceTraffic Tara — the 09:00 surge was the trigger. With pre-launch traffic, 5 connections were barely enough, so nothing failed between 08:58 and 09:01.
Key evidence Metric: DB active connections drop 42 → 5 at 08:59; DB CPU flat ~28%; payment p95 jumps to 30,000 ms; PayFast calls cap at ~450/min while traffic is ~1,200/min (throughput ceiling = saturation).
Logs: maximumPoolSize=5 (was 50 two days ago); Pool stats … idle=0, waiting=87; the timeout error.
Traces: failed trace — 30,000 ms in HikariPool.getConnection, no DB or PayFast span; slow success — 18.4 s waiting, then normal DB & PayFast times.
Innocent Postgres Pete: low CPU, fast queries (11.8 ms) — starved, not overloaded.
PayFast Priya: latency flat ~205 ms; failed traces never reach her.
Redis Rani: hit ratio flat 94%, carts fast (17 ms).
Disk-Full Dinesh: 97% for two days — a real issue, but an unrelated red herring (alert fatigue!).
FixRoll back to v2.3.0 (or set pool back to 50) — recovery within minutes.
PreventionLoad/performance test in CI · canary rollout with automatic rollback on SLO breach · alert on pool saturation (waiting > 0) · deployment events on dashboards · cost changes need reliability review · don't hold DB transactions across external calls · fix noisy alerts to avoid alert fatigue.
